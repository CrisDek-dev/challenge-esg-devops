1. Projeto testado

O projeto usado é a API do challenge ESG em C# (.NET 8), a mesma das atividades anteriores, com o tema eficiência energética e sustentabilidade. Ela recebe as leituras de consumo de energia dos equipamentos de cada setor de uma empresa, gera um alerta quando um setor passa do limite mensal de kWh, permite ligar e desligar equipamentos remotamente (só para ADMIN) e entrega um relatório de consumo por setor. O banco é SQL Server e a autenticação é feita com JWT.

Como o enunciado permite, os testes foram escritos em Java com Cucumber, seguindo a mesma arquitetura vista em aula (pastas features, steps, services, model, runner e hook). O projeto de testes fica na pasta testes-automatizados e é separado da API: ele faz requisições HTTP para a API rodando de verdade (local, em Docker ou no pipeline), do mesmo jeito que um cliente faria.

2. Relação dos testes com os pilares ESG

Cada funcionalidade recebeu uma tag com o pilar ESG que ela protege (@ambiental e @governanca). Assim os testes, além de garantir a qualidade técnica, verificam que a API continua cumprindo o seu papel dentro da proposta ESG.

PilarO que os testes garantem
Ambiental
(eficiência energética)		Leituras de consumo são registradas corretamente; o consumo acima do limite do setor gera alerta; o desligamento remoto funciona e equipamento desligado não registra consumo; o painel por setor mostra consumo e limites certos.
Governança
(integridade, rastreabilidade e compliance)		Ações críticas exigem autenticação (401 sem token); credenciais e dados inválidos são rejeitados; a resolução de um alerta registra a data (rastreabilidade) e não pode ser repetida; os contratos JSON Schema garantem que o formato das respostas não muda sem aviso para quem integra com a API.
Social
(usabilidade)		Os cenários negativos conferem que a API devolve mensagens de erro claras, que indicam ao usuário o que corrigir (ex.: "Email ou senha invalidos.", campo com erro de validação).

Fluxo de um passo: o Cucumber lê a linha do .feature e chama o método da classe de steps com a mesma frase. O step chama um service, que monta a requisição com Rest Assured e guarda a resposta no ContextoTeste. Os passos de validação (Então) leem essa resposta e conferem o status code, os campos do JSON e o contrato. Os passos que se repetem em todas as funcionalidades (status code, corpo, mensagem de erro e contrato) ficam em ComumSteps, para não duplicar código.

Testes independentes: cada cenário faz o próprio login e prepara os dados de que precisa (por exemplo, "que o equipamento 4 esteja ligado" liga o equipamento se ele estiver desligado). Por isso a suíte pode ser executada várias vezes seguidas, em qualquer ordem e no mesmo banco.

4. Cenários de teste em Gherkin

Os cenários foram escritos em português, no formato Dado - Quando - Então, com tabelas de dados (data tables) para os campos das requisições. Cada cenário tem uma tag que indica se é caminho feliz (@positivo) ou falha (@negativo), e os que validam contrato têm a tag @contrato. A tag @regressivo, aplicada em todas as funcionalidades, é a usada pelo TestRunner.

Os passos genéricos de validação ficam na classe ComumSteps. O passo "o corpo da resposta deve conter os valores" lê cada campo da tabela com o JsonPath do Rest Assured; números são comparados pelo valor (15000 é igual a 15000.00) e o restante como texto. import io.cucumber.java.pt.Quando;

import java.util.List;
import java.util.Map;

public class LeiturasSteps {

    private final LeiturasService leiturasService;
    private final AlertasService alertasService;

    public void queEuTenhaOsSeguintesDadosDaLeitura(List<Map<String, String>> rows) {

    public void deveExistirUmAlertaDeConsumoEmAbertoParaOSetor(String setor) {
        Assert.assertTrue("Nenhum alerta em aberto encontrado para o setor " + setor,
                alertasService.existeAlertaAbertoParaSetor(setor));
    }
}

6. Testes de contrato com JSON Schema

O teste de contrato garante que a estrutura da resposta (campos obrigatórios, tipos e formatos) continua a mesma, protegendo quem consome a API. Os contratos ficam em src/test/resources/schemas e usam o draft-07 do JSON Schema. Eles foram montados a partir das respostas reais da API, com os campos obrigatórios (required), os tipos (type) e additionalProperties: false, para que um campo novo ou renomeado também quebre o contrato.

7.4 Pipeline (GitHub Actions)

Foi adicionado o job Testes BDD (API) ao pipeline .github/workflows/ci-cd.yml da atividade de DevOps. Ele roda depois do build e dos testes unitários: sobe a API com SQL Server via docker compose, executa ./mvnw clean test, executa de novo pelo container de testes (validando o Dockerfile) e publica o relatório HTML como artefato. O job de imagem Docker agora depende dele (needs: [build-test, testes-bdd]), então se algum cenário falhar a imagem não é publicada e nada é implantado em staging ou produção.

  testes-bdd:
    name: Testes BDD (API)
    needs: build-test
    runs-on: ubuntu-24.04
    timeout-minutes: 25
    steps:
      - name: Checkout
        uses: actions/checkout@v7

      - name: Instalar Java 21
        uses: actions/setup-java@v6
        with:
          distribution: temurin
          java-version: "21"
          cache: maven

      - name: Gerar segredos do ambiente de teste
        run: |
          SA="Aa1$(openssl rand -hex 12)"
          JWT="$(openssl rand -hex 32)"
          echo "::add-mask::${SA}"
          echo "::add-mask::${JWT}"
          echo "SA_PASSWORD=${SA}" >> "$GITHUB_ENV"
          echo "JWT_SECRET_KEY=${JWT}" >> "$GITHUB_ENV"

      - name: Subir API + SQL Server
        run: docker compose -p esg-testes -f docker-compose.yml up -d --build

      - name: Executar testes BDD (mvn clean test)
        working-directory: testes-automatizados
        run: ./mvnw -B clean test -Dapi.baseUrl=http://localhost:8080

      - name: Executar testes BDD no container de testes (Dockerfile)
        run: >
          docker compose -p esg-testes -f docker-compose.yml -f docker-compose.testes.yml
          run --rm --build testes

      - name: Publicar relatorio dos testes BDD
        if: always()
        uses: actions/upload-artifact@v7
        with:
          name: relatorio-testes-bdd
          path: testes-automatizados/target/cucumber-reports.html

      - name: Encerrar ambiente de teste
        if: always()
        run: docker compose -p esg-testes -f docker-compose.yml -f docker-compose.testes.yml down -v || true

9. Evidências de execução

Execução local

A suíte foi executada no Windows 11 com o executar-api.bat (API em http://localhost:5000 com o SQL Server local) e o executar-testes-bdd.bat, que roda o mvnw clean test e abre o relatório HTML no final.

No relatório, cada cenário mostra os passos executados e a resposta da API guardada pelo Hook. Alguns exemplos de cenários positivos e negativos:

Teste de contrato detectando uma quebra

Para conferir que o teste de contrato realmente falha quando a resposta muda, o contrato equipamento.json foi alterado de propósito para esperar o campo ativo como texto ("type": "string"), enquanto a API devolve um booleano. O cenário falhou apontando a diferença ($.ativo: boolean encontrado, string esperado). Depois o contrato foi restaurado e a suíte voltou a passar.

Execução no pipeline (GitHub Actions)

Depois do push para a branch main, o pipeline executou automaticamente (execução nº 7, github.com/CrisDek-dev/challenge-esg-devops/actions/runs/40507804335). O job Testes BDD (API) subiu a API com SQL Server via Docker Compose e executou os 26 cenários duas vezes: pelo Maven (./mvnw clean test) e pelo container de testes (Dockerfile + docker-compose.testes.yml). Os dois passaram, e só então a imagem Docker foi publicada e os deploys de staging e produção foram executados.

10. Conclusão

Com o BDD, o comportamento esperado da API ficou descrito em português, de um jeito que dá para entender sem ler o código, e cada frase dos cenários virou um teste automatizado. Os 26 cenários cobrem todos os endpoints com caminhos felizes e de falha, validando status code, corpo da resposta e contrato com JSON Schema. Os testes também protegem as regras ligadas ao tema ESG do projeto: a geração de alertas quando o consumo passa do limite, o controle remoto dos equipamentos, o controle de acesso e a rastreabilidade da resolução dos alertas.

A execução é simples (um comando Maven, um .bat ou o Docker Compose) e foi integrada ao pipeline de CI/CD, onde os testes BDD funcionam como uma barreira de qualidade: se algum cenário falhar, a nova versão não é publicada nem implantada. Os 26 cenários passaram tanto na execução local quanto no GitHub Actions.
